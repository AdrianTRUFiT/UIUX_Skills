# Visual Convergence

## Mission

Do not merely implement a design. Make the rendered product visibly converge toward the intended standard while preserving the product's own identity, content, architecture, and functionality.

This skill exists because a technically correct build can still look generic, crowded, cheap, or visually incoherent.

## Governing Rule

REFERENCE → RENDER → COMPARE → CRITIQUE → CORRECT → RENDER AGAIN

Never declare visual completion from source code alone.

## Phase 1 — Establish the target

For each supplied reference, extract only transferable design evidence:

- hierarchy
- density
- composition
- whitespace
- typography scale and rhythm
- visual weight
- navigation behavior
- row/card anatomy
- depth, borders, shadows and surfaces
- color restraint
- motion language
- image/3D treatment
- interaction affordances
- mobile behavior

Do not copy trademarks, proprietary text, exact branded compositions, or unique protected artwork.

State the target in concrete visual terms. Avoid vague adjectives unless translated into observable behavior.

Bad: "make it premium."

Good: "one dominant portfolio number above the fold; no card grid in the first viewport; secondary system telemetry collapsed; primary action visually stronger than filters; typography creates hierarchy before borders do."

## Phase 2 — Capture the current product

Run the target application and capture the current state at relevant widths.

Minimum when practical:

- mobile ~390px
- tablet ~768px
- desktop ~1440px

Record the route and state used for comparison.

## Phase 3 — Produce a visual delta list

Compare current render against the target and list the most material differences in priority order.

Score each area 0–3:

0 = contradicts target
1 = weak / generic
2 = acceptable
3 = strongly aligned

Evaluate:

- first-viewport clarity
- hierarchy
- composition
- spacing rhythm
- typography
- surface treatment
- interaction clarity
- density
- responsiveness
- distinctiveness
- perceived product quality

Do not hide weak areas behind a global average.

## Phase 4 — Correct highest-leverage differences first

Fix structure before decoration.

Priority order:

1. wrong information hierarchy
2. wrong composition/layout
3. wrong density/spacing
4. wrong typography
5. wrong interaction treatment
6. wrong surface styling
7. decorative polish

Do not begin with shadows, gradients, radii, or animations when the hierarchy is wrong.

## Phase 5 — Preserve product truth

Visual changes must not fabricate:

- data
- status
- recommendations
- scores
- balances
- performance
- availability
- permissions

Do not replace working product state or architecture to chase a screenshot.

## Phase 6 — Render again

After each meaningful visual pass:

1. run the app;
2. capture the same route/state/viewport;
3. compare against the previous render and target;
4. identify what materially improved;
5. identify what remains visibly weak;
6. repeat.

A single implementation pass is not visual convergence.

## Phase 7 — Fresh-eyes gate

Before completion ask:

- Would a first-time user know what matters within 3 seconds?
- Is anything visually loud without being important?
- Does the screen look authored or assembled?
- Are typography and spacing doing more work than borders and boxes?
- Does the interface feel intentionally mobile rather than compressed desktop?
- Is there at least one memorable visual or interaction decision appropriate to the product?
- Does the result still look like a generic SaaS template?

If the answer to the final question is yes, continue.

## Required evidence at completion

Report:

- reference(s) used
- screenshots captured
- major visual deltas found
- major deltas corrected
- remaining intentional differences
- relevant repository verification results

Do not claim visual parity or premium quality without rendered evidence.
